# 巡检小车项目与开发对话交接

更新日期：2026-11-05。本文汇总项目结构、开发对话、验证记录和待排查问题，供接手者继续修改已有工程。先读本文及 [README](../README.md)，再用源码和设备核对具体问题。交接时已确认原工程 226 个可发布文件与仓库 `project/` 一致。

## 1. 先用一分钟理解项目

这是用于嵌入式比赛展示的体感/摇杆遥控巡检小车。四个麦克纳姆轮负责移动，顶部二维舵机云台带超声波探头扫描周围距离；车载四合一气体模块读取环境气体，ESP32-CAM提供画面。手持遥控器可以通过倾斜或摇杆控制，电脑/手机网页展示扫描、气体、轮速、行走轨迹，并保存路线及指定位置的扫描点图。

整体数据流：

手持 NodeMCU（MPU6050 / 摇杆）→ Wi-Fi UDP → 基座 ESP-01S → 串口 → STM32F407ZG → 电机、云台和报警输出。

传感器和编码器 → STM32 → 基座 ESP → HTTP → 2D/3D 网页。

ESP32-CAM加入同一热点，网页直接向摄像头取图，不经过STM32串口。

它是近距离巡检原型。超声波点图不是激光雷达建图；编码器路线不是GPS或SLAM定位；当前没有自动按保存路线驾驶。不能因为做了矿井展示场景，就宣称具备矿用防爆认证或已完成矿井实测。

## 3. 最容易被旧聊天误导的决定

### 3.1 基座与气体串口已互换

历史上基座曾接PA9/PA10，也曾在V8.10迁到PC10/PC11。最后V8.13为了适配PCB，再次交换基座与气体用途。当前源码是：

| 模块端 | STM32端 | 设置 |
| --- | --- | --- |
| 基座ESP RX | PA2 / USART2_TX | 115200，8N1 |
| 基座ESP TX | PA3 / USART2_RX | 115200，8N1 |
| 气体模块R/RX | PC10 / UART4_TX | 9600，8N1 |
| 气体模块T/TX | PC11 / UART4_RX | 9600，8N1 |

基座VCC、EN使用稳定3.3V；现有4MZ-HH4气体模块按项目资料使用稳定5V电源、3.3V串口逻辑；与主控共地。完整供电和其他接线读User/main.c当前接线表。V8.10文档中的“PC11接基座”现在是历史接法。遇到PC13之类问法，核对实际引脚，不要把PC11和PC13混为一谈。

### 3.2 自动复走已经删除，保存路线必须保留

曾做过上传保存路线、轮速闭环、自动重复行驶及多次方向修正。后来用户要求删掉自动行驶，V8.9已经移除其状态机、控制协议和网页入口；基座旧/api/route返回410。当前保留实时路线、保存/打开JSON、路线补传、位置扫描快照、手动驾驶与云台自动扫描。

“云台自动扫描”和“小车自动驾驶”是两回事。旧V7/V8.0等文档里的自动复走算法和参数不能当作当前启用功能，不要擅自恢复。

### 3.3 摄像头最近又改过方向

早期V1.2配置为CAMERA_VFLIP=1、CAMERA_HMIRROR=0。用户后来要求把画面反过来，V1.3 起采用 VFLIP=0、HMIRROR=1，相对于V1.2画面旋转180°。调整在传感器端完成，不要再在网页重复翻转。

仍为 320×240，默认 5 帧，支持 10/5/3 帧档。V1.4 可降 JPEG 体积、限帧及断流重试。改摄像头方向只需重烧摄像头，不要求重烧整车。没有实物验证记录时，不要说已经确认方向正确。

## 4. 手持遥控器与输入逻辑

实物使用NodeMCU ESP8266、MPU6050、ADS1115、双轴摇杆、SSD1306 OLED和电池供电板。

- D1/GPIO5是SCL，D2/GPIO4是SDA；MPU、OLED、ADS共用I2C。
- 摇杆X/Y接ADS1115 A0/A1，不是NodeMCU板载A0。ADS ADDR接地；摇杆SW接D5/GPIO14，按下接地。
- 摇杆、ADS及I2C侧按当前方案使用3.3V。原来5V接法曾导致摇杆不能正常就绪，后已按记录处理。
- 短按摇杆：体感云台 → 体感小车 → 摇杆小车 → 循环。
- 长按约0.8秒：请求软件停车。它不是独立硬件断电急停。
- 摇杆前后控制前进/后退，左右控制转向，不是横移；松手回中。
- 上电、切换、故障恢复都有输入有效性和回中检查。不要为了消除“中点异常”提示直接删掉检查。
- 本地摇杆模式编号3通过H1映射为车模式1；epoch用于识别模式切换。OLED本地请求状态不等于基座已执行。
- 目标发送周期20ms；这是配置目标，不是实测端到端延迟。

历史处理：按键消抖、短按/长按、ADS诊断、中点校准、摇杆左右方向，以及MPU初始化卡住都改过。V1.6把MPU初始化/校准改为分步状态机、有界I2C；原交接记录中用户已确认MPU问题解决。用户也明确说“按钮早就解决了”，不要把按钮故障继续当作后轮故障解释。

涉及方向先查HandheldInputConfig.h和CarConfig.h。不要同时改摇杆符号、电机极性、编码器符号、网页坐标来碰运气，否则会破坏已有标定。

## 5. 电机与后轮异常：保留的排查上下文

轮序固定：1左前、2右前、3左后、4右后。当前程序按四路PWM+DIR驱动板实现。

| 轮子 | PWM主控引脚 | DIR主控引脚 | 编码器A/B |
| --- | --- | --- | --- |
| M1 左前 | PC6 / TIM8_CH1 | PC4 | PE2 / PF8 |
| M2 右前 | PC7 / TIM8_CH2 | PC5 | PE3 / PF11 |
| M3 左后 | PE5 / TIM9_CH1 | PB12 | PF6 / PD6 |
| M4 右后 | PE6 / TIM9_CH2 | PB13 | PF7 / PD7 |

当前CarConfig.h：PWM 20kHz、占空比上限30%，电机符号{1,-1,1,-1}；失联250ms、主循环超时120ms、回中保持400ms且至少10个新包、换向停顿100ms。V8.16 体感输出在 30° 饱和，相对校准中心任一轴超过 75° 停车。短暂停车后回到 65° 以内可恢复，持续越界须回中。以上为代码配置，不是测速结果。电机不是串口设备，没有“轮子波特率”；不要把串口115200与PWM频率混用。

WheelSpeedConfig.h默认WHEEL_SPEED_ENABLE=0，轮速反馈用于监测，不能笼统宣称当前手控已启用四轮闭环等速。编码器A相上升沿计数，读取B相判方向，不能未经核对套用四倍频PPR。

用户实际反馈按大致先后归纳：
1. 起初后面两个轮子不转。
2. 只互换驱动板上前后轮的电机插头，主控控制线没动；随后后轮能转、前轮不转。
3. 后来出现3号轮前进“转一会停一下”，后退连续；进一步描述为3、4号轮前进断续、后退能转但速度不正确。
4. 用户说PWM波形完全一样，并问是否驱动板坏、该怎么测。
5. 用户问E3/E4编码器焊接、E1A/E2A连接影响，以及M+、M-、PWM、DIR分别是什么。
6. 用户提出从第一块PWM+DIR板换到另一块TB6612板；新板丝印是PWMA/B/C/D、AIN1/2、BIN1/2、CIN1/2、DIN1/2和STBY。

这些是用户反馈，不是已完成测量报告。目前可见记录没有证明最后换板成功，也没有证明后轮故障彻底修复。当前CarMotor.c仍每轮只输出一个DIR，不能声称已完成新板双方向输入适配。

接手排查应保留这些判断边界：
- 互换电机插头后故障跟随驱动输出通道，提示检查控制/驱动侧，但不能仅凭这一点确定芯片损坏。
- “PWM一样”还需确认测点、占空比及停顿时段；它不能排除DIR、驱动输入转换、供电、接触和输出级问题，也不能证明全部软件逻辑无关。
- 用户曾认为“肯定不是代码”，这是用户当时判断，不是已经证实的结论；应依据测量继续定位。
- M+和M-是一对电机功率输出，PWM/DIR是逻辑控制输入，编码器E*A/E*B是反馈；不能相互替代。
- 两块板同用TB6612，不代表接口直接兼容。必须先核对新板电路和STBY处理，再决定增加第二方向输出或使用经过验证的反相适配；不能把一个DIR同时接到IN1和IN2冒充互补方向。
- 现有源码和引脚表代表已实现的软件接口，不代表当前实车一定还按它接线。重新排查前确认用户现在用哪块板、烧了哪个版本。

## 6. 网页、路线和模拟演示

真实功能：2D/3D扫描、气体、四轮计数/RPM、估算路线、图传、路线保存与重新打开；停车后保存当前扫描点，在路线位置生成可点击红点，打开对应点图回看。

路线来自编码器，不是绝对定位。会受轮径、计数每圈、车架尺寸、方向标定和打滑影响。旧交接记录的初始参数为轮径97mm、左右轮中心距202mm、前后210mm、11PPR×34=374次/轮圈；接手仍须核对实际配置/网页标定，不能当作实测精度。

快照JSON version 2兼容读取旧version 1；最多100个扫描点、每点800个采样，文件上限20MB。保存当前扫描点只是加入内存，还需保存路线才写入文件。快照捕获当前缓存，不自动保证刚好完成一整轮扫描，也不包含气体和摄像头录像。不要删除桌面“路径保存数据库”的旧文件。

用户因车辆有问题要求增加完整模拟展示：保持原3D网页风格，播放行驶过程，多个路径点各自有不同扫描地貌，用于录展示视频。

V8.14 已提供本地模拟：

- 约2分13秒、13.15米、五个停车点，分别为双侧通道、转角、台阶、碎石、柱体。
- 支持暂停、重播、拖动进度、0.5/1/2/4倍速和录屏布局；路线红点可以回看扫描。
- rover-demo.js负责演示，点图来自预设几何场景的射线求交及微扰；不是现场采集。
- 入口为巡检模拟演示.html或gimbal-3d-scan.html?demo=1；提供完整模拟路线JSON。
- 演示不请求真实基座/摄像头、不发送车辆控制指令。页面和导出数据保留模拟标识。

聊天里出现过http://127.0.0.1:8766/gimbal-3d-scan.html?demo=1，这是当时电脑本地服务，不是公开网址，也不是换电脑后自动可用。基座内置页通常是http://192.168.4.1；完整扫描页面还依赖配套JS、模型文件。手机访问电脑页面需同网并使用电脑的局域网地址，不能在手机用127.0.0.1访问电脑。

用户还要求根据实体照片、SolidWorks装配文件、两个参考视频制作矿井碎石路段的3D展示视频。这是独立的演示资产需求，不能把网页模拟或渲染画面当成实车越障/矿井测试记录；成片和 Blender 工程在下文列出。

## 7. 气体、无线与验证边界

气体模块使用Modbus-RTU，涉及CH4、O2、CO、H2S。GasSensor.c处理CRC、浓度、小数位、单位、状态等；“在线”“浓度有效”“预热/故障/报警”不是同一件事。温湿度编码此前未确认，不能把原始寄存器直接当温湿度。

论文讨论中，曾出现 9.94 m、0.11～0.30 m/s、CO 44/69 ppm 等展示数值，来源未确认为实测，按模拟示例处理。源码能给出量程、阈值、周期和计算公式，无法推出现场浓度、检测精度、响应时间或实车速度。用户说“气体模块很灵敏”也不等于有响应时间/误差测量。

无线卡顿曾被讨论：旧基座 ESP8266 同步 HTTP 与 UDP 转发共用 loop。V4.10 改用分段 HTTP，V4.11 移除 HTTP 关闭时的 ACK 等待，并新增 UDP 接收间隔和主控串口诊断。STM32 V8.16 对串口接收故障立即停车，回中后恢复，见 [网络与图传复测](network-and-video.md)。图传虽独立取图，仍共享热点带宽；多页面轮询、供电和信号都可能影响体验。旧交接中“异步网络、所有帧加CRC、热点人数、停车重试”等属于曾提出后暂缓的建议，不能声称已经实现或已定位根因。测试控制延迟时记录是否开启视频及页面数量，并对照基座转发间隔。

当前工程没有证明每个遥测协议都带CRC。H1和其他协议分别看其实现；同名协议头在主控、基座、手持目录有多份，改协议时检查两端一致性。
