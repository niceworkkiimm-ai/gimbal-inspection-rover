# 给接手 AI 的工程交接说明

这份文档是根据项目开发对话和当前代码整理的摘要，不是逐字聊天记录，也不是实机测试报告。请先阅读这里和 README，再检查实际源码。用户希望你快速接手已有工程，而不是重新设计一套或恢复已经删除的功能。

## 用户想做什么

作品从“手持 MPU6050 体感控制二维舵机云台、超声波检测障碍物并报警”发展成了可移动巡检小车，作为嵌入式比赛作品，方向是地下/狭窄环境的近距离巡检展示。用户关注实际应用、完整工程实现和直观的网页展示，强调不要夸大事实。

小车为四轮麦克纳姆轮，1=左前、2=右前、3=左后、4=右后。驱动板为实际使用的 MD-TB6612 四路 PWM+DIR 接口版本，不是任意网上双路 TB6612 接线模板。轮径 97 mm、左右轮中心距 202 mm、前后轮中心距 210 mm、减速比 34:1；工程默认使用 11 PPR×34=374 次/轮圈的编码器配置，实际参数须以文件及标定核实。

## 当前版本和硬件分工

- STM32F407ZG：V8.13，8 MHz 外部晶振；负责舵机、超声波、四轮驱动/编码器、气体、TFT、报警输出与遥测。
- 基座 ESP-01S：V4.9，产生 Wi-Fi 热点，接收手持 UDP，双向转发 STM32 串口，提供 HTTP 控制/遥测接口。
- 手持 NodeMCU ESP8266 V3 CH340G：V1.6。MPU6050、SSD1306 OLED、ADS1115 共用 I2C；双轴摇杆由 ADS1115 读取，摇杆按压替代旧独立按键。
- 摄像头：普通 AI Thinker ESP32-CAM / ESP-32S，配 ESP32-CAM-MB 下载底板，固件 V1.2。历史 ESP32S3 目录不适合当前实物。
- 网页 V8.12：2D/3D 扫描、路线、气体、轮速、图传、扫描快照保存与回看。

三种手持控制：体感控制云台、体感控制小车、摇杆控制小车。短按摇杆循环切换，长按约 0.8 秒请求软件停车。手持本地模式编号 3 是摇杆，但发送给基座/STM32 的车模式与本地显示并非一一同号；修改前读完整 H1 帧生成代码，不要仅按屏幕文字猜协议。

## 最后一次硬件适配：V8.13 串口互换

用户在 PCB 中把基座与气体模块的串口位置互换，因此 2026-10-02 已修改 STM32：

| 设备信号 | STM32 对应引脚 |
|---|---|
| 基座 RX | PA2 / USART2_TX，115200 8N1 |
| 基座 TX | PA3 / USART2_RX，115200 8N1 |
| 气体 R/RX | PC10 / UART4_TX，9600 8N1 |
| 气体 T/TX | PC11 / UART4_RX，9600 8N1 |

`WirelessControl.c` 现在使用 USART2 及其 IRQ；`GasSensor.c` 使用 UART4 及其 IRQ，GPIO AF7/AF8 与 APB1 时钟配置已同步迁移。原收发队列、优先级、超时、协议和控制逻辑没有更改。此次仅需重烧 STM32；ESP 固件版本和网页不变。Keil 当时及本次发布副本构建均通过；这不构成 PCB 焊接或实机串口收发验证。

某些 ESP 文件头和历史文档仍写 PC10/PC11 接基座，属于旧记录。**以 `User/main.c` 顶部 V8.13 完整接线表和实际初始化代码为准。** STM32 的旧 USART1 PA9/PA10 已不用于当前基座通信。

## 建议按这个顺序阅读源码

所有路径相对 `project/`：

1. `User/main.c`：最前面的版本历史、完整供电和接线表，然后看初始化、主循环、舵机角度、测距、扫描和遥测调度。
2. `Hardware/WirelessControl.c/.h`、`HandheldProtocol.h`：H1 接收、模式切换、队列、帧到达时间、失联处理及 T/V/G2/E1/S1/J 系列数据。
3. `Hardware/CarMotor.c`、`CarLogic.c`、`CarConfig.h`：四轮 PWM/方向、混合输入、启动/回中/恢复及停车逻辑。不要凭“麦克纳姆”就宣称已经实现任意横移。
4. `Hardware/WheelEncoder.c`、`WheelSpeed*`、`RouteLog*`：计数、轮速、原生路线日志、补传协议；再核对网页 `vehicle-route.js` 和 `route-log.js`。
5. `Hardware/GasSensor.c`：四个通道的 Modbus-RTU 查询、CRC、原始浓度、小数位、单位、状态；`valid` 不等于环境安全，温湿度未确认编码，不能虚构数值。
6. `NodeMCU_Handheld_MPU_Car/`：主 ino、输入配置、摇杆/诊断、OLED，理解体感与摇杆的生成方式及校准状态机。
7. `ESP01S_Base_UDP/`：Wi-Fi 热点、手持 UDP → 串口、STM32 帧解析和网页接口。
8. `gimbal-radar-standalone.html`、`gimbal-3d-scan.html`、`vehicle-route.js`、`scan-snapshot.js`、`gimbal-model.js`、`camera-panel.js`：网页依赖和交互。
9. `ESP32CAM_Camera/`：板型、PSRAM、取图时序、上下翻转、摄像头 Wi-Fi；不要选择历史 S3 固件。

仅 `Gimbal_STLink.uvprojx` 是当前 Keil 工程入口。先核对 XML 所列文件和 build target，不能拿旧 project 工程当最新版。

## 开发对话中的重要决定

- 项目已完成多轮方向修正：手持倾斜、小车前后/转向、摇杆 X 方向、网页角度和三维上下方向都曾调整。当前配置应当保留；新问题先看数据与实物，不要全局反转全部坐标。
- 用户曾遇到长时间卡住、TFT 白屏和上电需要复位等问题，已做过多轮修正。超声波代码使用 DWT 原始周期无符号差值处理回绕，测距有超时；不要退回旧绝对时间比较方案。
- 手持 PCB 上 MPU6050 曾使启动很慢，后改为分步初始化/校准和有界 I2C 事务；用户后来明确说 MPU 问题已经解决。它不是当前待修问题，不要擅自重做。
- 手持摇杆必须按现有设计使用 3.3V，曾因接 5V 导致未就绪；已解决。当前左右反向修正放在 `HandheldInputConfig.h`。
- 用户曾尝试“自动按照保存路线重复行驶”，但体验不佳，**V8.9 按要求已删除自动行驶功能，保存/打开路线必须保留**。不要把文件名含“复走”的旧文档当作当前功能。
- 里程路线是编码器估算，不是 GPS 或 SLAM。原地转向路线漂移相关判断经历过核对与修正，不能只凭旧聊天断言仍有相同故障。
- 3D 点数和打点间隔、雷达量程曾多次调整；当前代码才是依据，不要从早期 50/60/150/400 cm 请求中挑一个值直接覆盖。
- 距离分级需求为 20 cm 内红色报警、20–40 cm 黄色注意、40 cm 以上绿色；具体边界和无效测距以当前程序为准。
- 页面抬头曾按用户要求改为“嵌入电团队”。界面要中文、清晰、直观，避免增加一堆名称相似的保存按钮。

## 路线与扫描快照：必须保留的最新网页功能

用户希望：小车在某位置扫描后，保存当时点图；路线该位置出现可点的标记，点击可回看当时点图；路线和快照一起保存到本地，关机/重开页面后仍可打开。

当前 V8.11/V8.12 已从提供的更新版本同步此功能：

- 路线 JSON `version: 2` 包含扫描快照和当时位姿；兼容旧 version 1 路线。
- 记录上限 100 个位置，每份快照最多 800 个采样；导入文件有大小和结构校验。
- 抓取快照要求在线、新鲜数据、确认过的路线标定与原生路线同步状态。
- 点击记录后回看，三维视图可旋转/缩放；V8.12 通过 `gimbal-model.js` 统一实时和回看模型。
- “保存当前扫描点”是先加入内存中的路线记录；还需要“保存路线”才能持久化到本地文件。
- 保存现有点缓存，不保证缓存恰好是一轮完整扫描；气体与摄像头画面不随扫描快照存档。
- `tests/route-snapshot.test.cjs` 是现有 7 项回归测试。请维护兼容性，不要重新引入已经删除的自动行驶。

## 用户的协作偏好

- “先分析/先计划/只是请问”时先说明，不要提前改代码；明确说修改才实现。
- 修改应限定到当前指定工程。保留原位置、原文件；需要备份、工具和构建临时文件都放 D 盘。
- 每次业务修改更新版本号以及主函数开头的完整接线注释，包括手持端和电源，不只写 STM32 信号线。
- 发接线时用表格或逐行对应，必须含供电、共地、按钮、运行/烧录区别，用户不喜欢接线信息散在大段文字里。
- 说明到底需要重新烧录哪些设备，给正确入口；编译通过和已烧录成功必须区分。
- 不要声称“全读过”“已验证硬件”但没有证据；保持简明的过程更新，网络中断后继续未完成工作。
- 用户授权后续每次完成并验证的修改，以清楚的提交说明保存版本并推送这个独立 GitHub 仓库。不要推到工创仓库。

## 本仓库与原工作工程的关系

原工程绝对位置只保存在 `.local/config.json`，不会上传。`project/` 为同步副本，业务逻辑及必要资源保持原样，仅有明确的公开脱敏：密码头文件引用、文档密码占位、个人路径占位及小程序测试 AppID。工具、版本管理及差异备份都在 D 盘。

接手时先看 `git status`、最近提交、`.local/config.json`（存在时）和源工程实际文件。不要直接在 D 盘受控副本改业务代码后强行执行同步；同步器会为保护该修改而拒绝覆盖。按用户指示在原工程完成修改与验证，再执行 `tools/project_sync.py publish --message "说明具体修改"`。这个程序不负责确认实车运动正常，需把实际验证情况写清楚。
